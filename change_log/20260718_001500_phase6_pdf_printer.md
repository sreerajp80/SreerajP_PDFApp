# Change log — Phase 6: PDF printer for Android ("print to PDF")

**Date:** 2026-07-17
**Implements:** `plans/20260717_114932_phase6_pdf_printer.md`
**Plan in:** `docs/pdf-app-implementation-plan.md` §5, Phase 6

---

## What changed, in short

The app was a one-way street: only PDFs could come in, and nothing could go out to paper. Now:

1. **Other apps can send pictures or text here and get a PDF.** Share one image, many images, or
   plain text into the app; it builds a brand-new PDF and the user saves it wherever they like
   through the normal system save dialog.
2. **A PDF can be printed out.** A new **Print** entry in the viewer menu prints the whole
   document, a chosen page range, or the document's text, using Android's own print dialog.
3. **The system print service was dropped** — on purpose. See the decisions below.

The original file is never touched anywhere in this work: every path writes a new file.

## Native (Kotlin)

- **New `PrintHandler.kt`** — hands a finished PDF to Android's `PrintManager` through a
  `PrintDocumentAdapter` that streams the file. Android draws the whole print dialog (printer,
  copies, paper, and its own built-in "Save as PDF" printer), so the app builds none of that.
  Also answers `isPrintingAvailable` so the UI never offers a dialog that cannot come.
- **`PdfBoxHandler.kt`** — added `imagesToPdf` (one A4 page per picture, scaled to fit, big
  photos sampled down while decoding so the heap survives), `textToPdf` (word-wrapped A4 pages),
  and `canWriteTextToPdf`.
- **`MainActivity.kt`** — registers the print handler; now also accepts `image/*` (single and
  multiple) and `text/plain` shares, plus text shared with no file behind it. Every intent
  payload carries a `kind` (`pdf` / `images` / `text`) so Dart knows where to send it. A share we
  cannot read is ignored rather than crashing.
- **`AndroidManifest.xml`** — share filters for `image/*` and `text/plain`, and
  `SEND_MULTIPLE` for `image/*`. This is what puts the app in other apps' share sheets.

## Dart

- **New `lib/features/printer/`** — `printer_channel.dart` (print bridge), `pdf_builder_service.dart`
  (shared content → new PDF in the `printer/` cache), `print_service.dart` (print whole / range /

  breaks.
- **`core/platform/pdfbox_channel.dart`** — `imagesToPdf`, `textToPdf`, `canWriteTextToPdf`, and
  `unsupported_text` mapped to a typed exception.
- **`core/errors/app_exception.dart`** — new `PdfUnsupportedTextException` and `PrintException`.
- **`core/constants/app_constants.dart`** — printer cache folder, import picture limit.
- **`features/viewer/`** — Home routes shared pictures/text to the Import screen and PDFs to the
  viewer as before; the viewer menu gained **Print**; `pdf_repository` follows the new types.
- **`app/routing/app_router.dart`** — new `import` route.
- **`l10n/`** — new English and Malayalam strings for the import and print flows.

## Decisions worth knowing

- **No new package.** Android's print framework is an OS API, and PdfBox was already in the build,
  so nothing new was needed. The `printing` package (Apache 2.0) would also have worked — on
  Android it wraps the same `PrintManager` / `PrintDocumentAdapter` we use, with no native code of
  its own. We wrote our own because the app already owns a native-channel path (PdfBox, TTS, SAF)
  and this fits it, not because `printing` was unusable. *(Corrected — see below.)*
- **System print service dropped.** An Android `PrintService` is built to drive *real* printers —
  discover them, report capabilities, handle their jobs. It is not how an app becomes a "save as
  PDF" target, and Android's print dialog already ships its own built-in "Save as PDF" printer.
  Step 1 covers the real need, so a print service would be a lot of risky native code for almost
  no user gain. Recorded in `docs/architecture.md §16`; marked `[-]` in the tracker.
- **A page range is sliced before printing,** using the existing tested `organizePages` call,
  rather than making the print adapter re-cut the document. Same result, far less native risk.
- **Text → PDF only writes Latin-1 letters.** PdfBox-Android ships Latin-1 built-in fonts and has
  no complex-script shaping engine, so Malayalam or Devanagari text would throw or come out as
  broken glyphs. The app checks first and explains plainly instead of saving nonsense. A
  *picture* of Malayalam text saves fine. This is a real limit of the open-source stack, not a
  bug, and lifting it would mean bundling a font plus a shaping engine.

## A bug found and fixed while building

Each print action closed the sheet and then used the sheet's own `BuildContext` after an
`await`. A scratch test confirmed the context stays mounted for a short await but is **gone once
the pop animation finishes (~300 ms)** — so a slow platform reply would have made the print
silently do nothing, while a fast one worked. That is the worst kind of bug: fine on a quick
device, broken on a slow one. The sheet now captures the messenger, navigator, and strings before
it closes and never touches the dead context. `print_sheet_test.dart` covers it.

## Correction (2026-07-17, after this log was first written)

This log originally said the `printing` package "bundles a second copy of PDFium and would clash
with `pdfrx`", and gave that as the reason for writing our own print bridge. **That was false**,
and it was written as a checked fact when it had not been checked.

On Android, `printing` (5.14.3) has no PDFium, no `.so` files, and no third-party Gradle
dependencies — its Android side is five Java files wrapping `PrintManager` /
`PrintDocumentAdapter` and `android.graphics.pdf.PdfRenderer`, the same OS APIs `PrintHandler.kt`
uses. The claim came from `printing`'s Windows and Linux builds, which *do* link PDFium,
generalised to Android without looking. This app is Android-only, so it never applied. The app has
exactly one copy of PDFium, from `pdfrx`; adding `printing` would not have added a second.

Nothing in the code changed: `PrintHandler.kt` still stands, on the ordinary grounds now stated
above. Only the recorded reason was wrong, which matters because a future reader would have taken
it as verified and never re-checked it. Corrected by
`plans/20260717_134828_fix_printing_package_claim.md` and
`change_log/20260717_135500_fix_printing_package_claim.md`.
