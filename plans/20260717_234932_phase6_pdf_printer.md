## 1. What the issue is

The app can open, read, extract from, edit, and annotate PDFs. But it is still a one-way
street:

1. **Nothing can come *in* except a PDF.** If another app shares a picture or some text, we
   ignore it. The product idea says this app should be the place where other apps send
   content **to be saved as a PDF**.
2. **Nothing can go *out* to paper.** There is no way to print an open PDF on a real printer.
   Android has a standard print framework; we simply do not use it yet.
3. **Other apps' "Print" menus cannot target us.** That needs a native Android *print
   service*, which the main plan already marks as "later, riskier".

---

## 2. What we will build

Built in the risk order given by the main plan.

### Step 1 — Share / "Open with" → save as PDF

Register the app as a share target for content that can become a PDF:

- `image/*` — one image or many (`ACTION_SEND` and `ACTION_SEND_MULTIPLE`).
- `text/plain` — shared text, both as `EXTRA_TEXT` and as a `text/plain` file.

Flow: content arrives → native reads it → builds a **new** PDF in the app cache with
PdfBox-Android → Dart shows an import screen (what came in, how many pages) → user taps
**Save as PDF** → existing SAF `saveToDevice` writes it wherever the user chooses. Copy-on-write
holds: we only ever read the incoming content and write a brand-new file.

**Images →** one page per image, page sized to the image, scaled to fit an A4-ish page with a
small margin, aspect ratio kept. JPEG/PNG/WebP go through Android's own decoder, so anything the
system can show, we can place.

**Text →** wrapped lines on A4 pages with a standard font.

> **Important limit — non-Latin text.** PdfBox-Android's built-in fonts are Latin-1 only, and
> PdfBox has no complex-script shaping engine. Malayalam or Devanagari text **cannot** be
> written to a PDF correctly this way — it would either throw or produce broken glyphs. So the
> text→PDF path checks the shared text first: if it is not writable in Latin-1, we show a clear
> message ("this text cannot be saved as a PDF yet — the letters are not supported") and offer
> nothing broken. This obeys "never crash on bad input" and "never a dead button". Images are
> unaffected — a picture of Malayalam text saves fine.

### Step 2 — Print a PDF out

A new native `PrintHandler` on the already-reserved channel `in.sreerajp.pdfapp/print`, using
Android's `PrintManager` with a `PrintDocumentAdapter` that streams an existing PDF file to the
print spooler. Android draws the print dialog (printer choice, copies, paper, and its own
"Save as PDF" printer) for free.

From the viewer's overflow menu, a new **Print** entry offers:

- **This document** — prints the open PDF as-is.
- **Page range** — the user picks a range; we first build a new range-only copy with the
  existing PdfBox `organizePages` call, then print that copy. This is deliberate: making the
  adapter honour the spooler's own page ranges is fiddly and easy to get subtly wrong, and we
  already have a tested, copy-on-write way to slice pages.
- **Extracted text** — uses the existing extraction service, runs the text through the same
  text→PDF builder as Step 1 (with the same non-Latin guard), then prints that.

The temp files live in the app cache and are cleared like the other page-op outputs.

### Step 3 — System print service

**Deferred, and recorded as deferred.** An Android `PrintService` exists to talk to *real*
printers — it must discover printers, report their capabilities, and hand back print jobs. It is
not a way to be a "save to PDF" target; Android's print dialog already ships its own built-in
"Save as PDF" printer, so a print service here would add real risk and native complexity for
almost no user gain. Step 1 (share → save as PDF) covers the actual need. This will be marked
`[-]` in the tracker with that reason, and the phase's "Done when" note in the main plan already
allows it ("step 3 tracked as a follow-up if deferred").

## 4. Rules this obeys

- **Open source only** — no new package. Android's print framework is an OS API; PdfBox
  (Apache 2.0) is already in the build, so nothing new is needed. *(Corrected — see the note
  under the Status block. This bullet originally claimed the `printing` package bundles its own
  pdfium and would fight with `pdfrx`. That was false.)* The `printing` package (Apache 2.0)
  would also have worked; we write our own because the app already owns a native-channel path
  (PdfBox, TTS, SAF) and this fits it.
- **Copy-on-write** — every import and every print prep writes a new file in the cache; nothing
  incoming is ever modified.
- **Scoped storage only** — content comes in via share intents; output goes out via SAF
  `saveToDevice` or the print spooler. No browsing, no storage permission.
- **Never crash** — unreadable images, empty shares, non-Latin text, no printer available, and
  a cancelled print dialog all map to friendly states.
- **Offline** — nothing here touches the network.
- **Heavy work off the UI isolate** — image decode and PDF building already happen on the native
  side, off the Flutter UI thread.

## 5. Done when

- Sharing one image, several images, or plain text into the app produces a valid PDF the user
  can save anywhere through the system save dialog; the original is untouched.
- Non-Latin shared text gives a clear message instead of a crash or garbage.
- The viewer's **Print** menu prints the whole document, a chosen page range, and extracted
  text through Android's print dialog.
- Step 3 (system print service) is marked deferred in the tracker with the reason above.
- `flutter analyze` clean, `dart format` clean, all tests pass, dev APK builds.
